# 2026-08-21 夯实地基清洁度与隔离说明

## 背景

夯实地基已经在多个项目中证明有效，但在跨项目复用后，开始出现一个新的问题：

- 方法论本身是对的
- 但部分 AI 会觉得它“有些脏”

这里的“脏”通常不是指方法论失效，而是指通用规则、项目专属知识、历史踩坑记录、一次性会话产物混在一起，导致后续 AI 在读取时无法准确区分哪些可以继承，哪些只能局部适用。

## “脏”到底是什么意思

### 1. 语义脏

同一个“夯实地基”名义下混入了不同层级的内容：

- 通用协议
- 项目规则
- 临时观察
- 历史结论
- 已废弃方案

当这些内容没有分层时，AI 会把项目私货误读成通用原则。

### 2. 上下文脏

某个项目中验证成立的知识，被另一个项目无条件继承。

常见表现：

- 某个 API 的参数限制，被误当成所有项目都要遵守
- 某个语言模型的提示词经验，被误用到另一类模型
- 某个仓库结构要求，被误读为全局规范

### 3. 状态脏

已验证结论、待验证猜测、历史尝试、废弃方案写在一起，但没有状态标签。

后续 AI 很容易：

- 复用过时方案
- 把猜测当结论
- 把一次性 workaround 当长期规则

### 4. 入口脏

不同项目都要求“先读夯实地基”，但没有定义：

- 先读哪一层
- 哪些是通用
- 哪些是项目隔离内容
- 哪些不能跨项目带走

结果就是知识串味。

## 结论

别人说夯实地基“有些脏”，大概率不是说它没价值，而是说当前版本的边界还不够硬。

更准确地说，是以下三类东西没有彻底分仓：

- 通用方法论
- 项目专属知识
- 历史杂质与踩坑记录

## 正确的隔离结构

夯实地基后续应至少拆成四层。

### Layer 1: Foundation-Core

只放跨项目通用的稳定规则。

例如：

- 需求点必须绑定知识入口
- 实施前必须先有方案
- 完成前必须有验证目标
- 审计结论必须与实现分开
- 已验证与未验证信息必须分层

这一层可以跨所有项目复用。

### Layer 2: Foundation-Project

只放单个项目的专属结构。

例如：

- 项目需求文档
- 项目 KB 索引
- 项目能力边界
- 项目适配过的工作流
- 项目确认有效的实现约束

这一层必须项目隔离，不能默认外带。

### Layer 3: Foundation-Learnings

只放踩坑记录、实验、观察、经验转译。

例如：

- 某次 API 实测失败结论
- 某类 prompt 的试错记录
- 某个模型在某种约束下的异常行为
- 某项功能的经验概率判断

这一层可以被读取，但不能自动升格为规则。

### Layer 4: Foundation-Deprecated

只放废弃内容。

例如：

- 已废弃模板
- 已失效推断
- 被新验证否定的旧策略
- 旧版本协议

这一层保留追溯价值，但默认不参与当前决策。

## 后续 AI 的读取顺序

如果未来项目采用这套结构，标准入口顺序应为：

1. 先读 `Foundation-Core`
2. 再读当前项目的 `Foundation-Project`
3. 如需求点有绑定，再读对应 `Foundation-Learnings`
4. 只有在追溯历史时才读 `Foundation-Deprecated`

这个顺序的目的，是保证 AI 不会一上来就被历史噪音污染。

## 识别污染的最小规则

如果一条内容无法回答下面三个问题之一，它就不应进入 Core：

1. 这是通用规则，还是项目局部结论
2. 这是已验证，还是待验证
3. 这是当前有效，还是历史保留

回答不清，就不能放进核心层。

## 实施建议

下一步不应继续泛泛补文档，而应做结构化清理。

建议顺序：

1. 先定义四层目录或四类标签
2. 先把现有“通用规则”抽到 `Foundation-Core`
3. 再把每个项目自己的知识绑定到 `Foundation-Project`
4. 再把踩坑记录和实验迁移到 `Foundation-Learnings`
5. 最后把已废弃内容沉到 `Foundation-Deprecated`

## 判断标准

如果完成这次分层后，新的 AI 进入任一项目时能够明确知道：

- 什么能直接继承
- 什么必须只在当前项目里使用
- 什么只是经验，不是硬规则
- 什么已经废弃

那就说明夯实地基从“有效但容易串味”，升级成了“有效且可持续复用”。
